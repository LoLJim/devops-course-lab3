### 1.2. Схема взаимодействия
```
Makefile — единая точка входа. Он не содержит логики, а только делегирует:
каждая цель (install, test, build и т.д.) вызывает соответствующий скрипт 
bash scripts/<имя>.sh.

Bash-скрипты — исполнители. Каждый скрипт подключает общий модуль 
common.sh через source, получая строгий режим (set -euo pipefail), функции 
логирования и проверок.
```

## 2. Настройка Python-проекта

### 2.1. Роль pytest.ini
```
Файл pytest.ini нужен, чтобы pytest правильно находил модули проекта. 
Директива testpaths = tests указывает, где искать тесты, а 
pythonpath = src автоматически добавляет каталог src в sys.path при 
запуске тестов — благодаря этому в тестах можно писать чистые импорты вида 
from calculator import add, не прибегая к sys.path.insert.

Это решает сразу две проблемы: во-первых, исчезает ModuleNotFoundError, 
когда тесты из tests/ не видят модули из src/; во-вторых, уходит ошибка 
E402 от flake8, которая появлялась из-за sys.path.insert посреди файла. 
В итоге не нужен ни лишний conftest.py, ни ручной PYTHONPATH=src pytest — 
всё настраивается один раз в pytest.ini.
```

### 2.2. Конфигурация flake8
```
max-line-length = 88
extend-ignore = E203
exclude =
    .venv,
    __pycache__,
    .git,
    .pytest_cache,
    .mypy_cache,
    htmlcov

max-line-length = 88 — максимальная длина строки 88 символов 
(стандарт black), а не дефолтные 79.

extend-ignore = E203 — отключает проверку E203 («whitespace before ':'»), 
потому что black и flake8 иначе конфликтуют при форматировании срезов.

exclude — список каталогов, которые линтер не проверяет: виртуальное 
окружение, кеши, .git, отчёты покрытия.
```

## 3. Bash-скрипты

### 3.1. common.sh — общий модуль
```
Логирование (пишут и в stdout с цветом, и в logs/automation.log с 
таймстампом):

    log_info — синее [INFO], обычные сообщения
    log_success — зелёное [OK], успешное завершение
    log_warning — жёлтое [WARN], некритичные проблемы
    log_error — красное [ERROR] в stderr, ошибки

Проверка зависимостей:

    require_command <cmd> — проверяет одну команду, возвращает 1, если нет
    require_commands <cmd1> <cmd2> ... — проверяет список, собирает все 
отсутствующие и сообщает о них разом

Оформление вывода:

    print_header "<title>" — рамка с заголовком (двойная линия)
    print_separator — горизонтальная линия-разделитель

Работа со временем:

    measure_time <команда> — запускает команду, замеряет секунды, 
логирует «Время выполнения: Nс» и возвращает её код

Идемпотентность:

    ensure_dir <dir> — создаёт каталог, только если его нет (mkdir -p + лог)
    ensure_line_in_file <file> <line> — добавляет строку в файл, только 
если её там ещё нет (grep -qF)
```

## 4. Docker-образ

### 4.1. Структура Dockerfile
```
FROM python:3.11-slim

# Предотвращаем создание .pyc файлов и буферизацию вывода
# PYTHONPATH нужен, чтобы импорты работали так же, как локально с pytest.ini
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PYTHONPATH=/app/src

WORKDIR /app

# Установка зависимостей (кэшируется, если requirements.txt не меняется)
COPY requirements.txt .
RUN pip install --no-cache-dir --upgrade pip && \
    pip install --no-cache-dir -r requirements.txt

# Копирование исходного кода
COPY src/ ./src/

# Создание непривилегированного пользователя
RUN useradd -m --uid 1000 appuser && \
    chown -R appuser:appuser /app

USER appuser

EXPOSE 8000

CMD ["python", "src/main.py"]

```

### 4.2. Роль PYTHONPATH
```
PYTHONPATH=/app/src добавляет каталог src в путь поиска модулей Python
внутри контейнера. Без неё python src/main.py падает с
ModuleNotFoundError: No module named 'calculator' — контейнер не стартует.
Локально это не видно, потому что pytest.ini подставляет src сам,
а в Docker про него никто не знает.
```

## 5. Makefile

### 5.1. Структура Makefile
```
# ==============================================================================
# Makefile для проекта Calculator
# ==============================================================================

# ==============================================================================
# Переменные конфигурации
# ==============================================================================

PROJECT_NAME := calculator
PROJECT_VERSION := 1.0.0

SCRIPTS_DIR := scripts
LOGS_DIR := logs

IMAGE_NAME := $(PROJECT_NAME)
IMAGE_TAG := $(PROJECT_VERSION)
CONTAINER_NAME := $(PROJECT_NAME)-container

export IMAGE_NAME
export IMAGE_TAG
export CONTAINER_NAME

# ==============================================================================
# Фиктивные цели
# ==============================================================================

.PHONY: help check-deps install test lint format build run clean info \
        all dev test-all rebuild logs stop status clean-all version

# ==============================================================================
# Цель по умолчанию — справка
# ==============================================================================

.DEFAULT_GOAL := help

# ==============================================================================
# Справка
# ==============================================================================

## help: Показать эту справку
help:
	@echo ""
	@echo "╔════════════════════════════════════════════════════════════╗"
	@echo "║  $(PROJECT_NAME) v$(PROJECT_VERSION) — доступные команды                 ║"
	@echo "╚════════════════════════════════════════════════════════════╝"
	@echo ""
	@echo "  Основные команды:"
	@grep -E '^## [a-zA-Z_-]+: ' $(MAKEFILE_LIST) | \
		sort | \
		awk 'BEGIN {FS = ": "}; {printf "    \033[36m%-15s\033[0m %s\n", $$1, $$2}' | \
		sed 's/^## //'
	@echo ""
	@echo "  Примеры:"
	@echo "    make install          — установить зависимости"
	@echo "    make test             — запустить тесты"
	@echo "    make build            — собрать Docker-образ"
	@echo "    make run              — запустить контейнер"
	@echo "    make dev              — полный цикл разработки"
	@echo ""

# ==============================================================================
# Основные цели
# ==============================================================================

## check-deps: Проверить наличие всех необходимых инструментов
check-deps:
	@bash $(SCRIPTS_DIR)/check-deps.sh

## install: Установить зависимости проекта
install:
	@bash $(SCRIPTS_DIR)/install.sh

## test: Запустить тесты
test:
	@bash $(SCRIPTS_DIR)/test.sh

## lint: Запустить статический анализ кода
lint:
	@bash $(SCRIPTS_DIR)/lint.sh

## format: Отформатировать код
format:
	@bash $(SCRIPTS_DIR)/format.sh

## build: Собрать Docker-образ
build:
	@bash $(SCRIPTS_DIR)/build.sh

## run: Запустить Docker-контейнер
run:
	@bash $(SCRIPTS_DIR)/run.sh

## clean: Очистить артефакты сборки
clean:
	@bash $(SCRIPTS_DIR)/clean.sh

## info: Показать информацию о проекте
info:
	@bash $(SCRIPTS_DIR)/info.sh

# ==============================================================================
# Составные цели
# ==============================================================================

## all: Полный цикл: установка, линтинг, тесты, сборка
all: install lint test build

## dev: Цикл разработки: установка, форматирование, линтинг, тесты
dev: install format lint test

## test-all: Линтинг + тесты
test-all: lint test

## rebuild: Пересобрать образ (остановить, удалить, собрать заново)
rebuild: stop clean build

# ==============================================================================
# Управление контейнером
# ==============================================================================

## stop: Остановить контейнер
stop:
	@docker stop $(CONTAINER_NAME) 2>/dev/null || true
	@docker rm $(CONTAINER_NAME) 2>/dev/null || true
	@echo "Контейнер остановлен"

## logs: Показать логи контейнера
logs:
	@docker logs -f $(CONTAINER_NAME)

## status: Показать статус контейнера
status:
	@docker ps -a --filter "name=$(CONTAINER_NAME)" --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"

# ==============================================================================
# Утилиты
# ==============================================================================

## clean-all: Полная очистка (включая логи)
clean-all:
	@CLEAN_LOGS=true bash $(SCRIPTS_DIR)/clean.sh

## version: Показать версию Makefile
version:
	@echo "$(PROJECT_NAME) automation v$(PROJECT_VERSION)"

```

## 7. Идемпотентность

### 7.1. Примеры идемпотентных операций
```
1. isntall.sh
if [ ! -d ".venv" ]; then
    python3 -m venv .venv
fi

Venv создаётся только один раз. Повторный make install не пересоздаёт 
окружение и не ломает уже установленные пакеты.

2. run.sh
if docker ps -a --format '{{.Names}}' | grep -q "^${CONTAINER_NAME}$"; then
    docker stop "$CONTAINER_NAME" || true
    docker rm "$CONTAINER_NAME" || true
fi

Проверка «существует ли контейнер» + || true гарантируют, что повторный 
make run не упадёт с «container name already in use».

3. clean.sh

if docker image inspect "$FULL_IMAGE" > /dev/null 2>&1; then
    docker rmi "$FULL_IMAGE" || true
fi

Образ удаляется, только если он есть. Если образа нет — скрипт молча идёт 
дальше, make clean не падает.
```

## 10. Ответы на контрольные вопросы
```
1. Зачем set -euo pipefail? Что делает каждая директива?
Строгий режим для надёжности. -e — прервать при ошибке, -u — ошибка при 
обращении к неустановленной переменной, -o pipefail — код пайпа = код 
последней упавшей команды. Без них ошибки «проглатываются».

2. Разница между идемпотентностью и воспроизводимостью? Примеры.
Идемпотентность — повторный запуск не меняет результат (mkdir -p, grep -q 
|| echo >>). Воспроизводимость — одинаковый результат на другой 
машине/окружении (фиксированные версии в requirements.txt, Dockerfile).

3. Зачем pytest.ini с pythonpath = src?
Добавляет src в sys.path при запуске тестов. Решает ModuleNotFoundError и 
убирает sys.path.insert, из-за которого flake8 выдаёт E402.

4. Зачем PYTHONPATH=/app/src в Dockerfile?
Чтобы Python в контейнере находил модули в /app/src. Без неё — 
ModuleNotFoundError: No module named 'calculator', контейнер падает.

5. Зачем common.sh? Преимущества.
Общий модуль с логированием, проверками и строгим режимом. Даёт 
единообразие, устраняет дублирование, упрощает поддержку — правка в одном 
месте.

6. Зачем .PHONY в Makefile?
Цели, не создающие файлов (install, test, run), объявляются фиктивными. 
Иначе Make может спутать цель с одноимённым файлом и не выполнить её.

7. Как работает автогенерация make help?
grep -E '^## цель: ' выбирает строки-комментарии, awk форматирует, sort 
сортирует, sed убирает ##. Получается список целей с описаниями.

8. Почему Makefile должен делегировать логику скриптам?
Makefile — оркестратор, не исполнитель. Сложная логика в Bash читаемее, 
тестируемее и переносима. Makefile остаётся тонким и понятным.

9. Как обеспечить идемпотентность «добавить строку в файл»?
grep -qF "$line" "$file" || echo "$line" >> "$file" — строка добавится 
только если её ещё нет. Дубликатов не будет.

10. Зачем логирование? Какие уровни использовали?
Логи фиксируют ход выполнения для отладки и аудита. Использовали четыре 
уровня: INFO, OK (success), WARN, ERROR — с цветом в консоли и таймстампом 
в logs/automation.log.
```
